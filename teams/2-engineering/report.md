# گزارش تیم مهندسی — جواب‌سریع (JavabFast)

## خلاصه (۳ خط)
- پیشنهاد: یک سرویس یکپارچه (Node/TypeScript) با وب‌هوک، صف Redis و PostgreSQL؛ پاسخ‌ها از کاتالوگ فروشگاه ساخته می‌شوند و در موارد نامطمئن به انسان می‌روند.
- طرح داده و اتصال به API اینستاگرام (OAuth، وب‌هوک امضادار، پنجره ۲۴ ساعته) آماده است، ولی جزئیات Meta باید با مستندات رسمی راستی‌آزمایی شود.
- بزرگ‌ترین ریسک: دسترسی و تأیید اپ Meta (App Review، Business Verification) برای تیم و مشتریان ایرانی؛ هنوز بررسی نشده.

## طرح نگار (معمار نرم‌افزار)

**پشته پیشنهادی (MVP):**
- **بک‌اند:** Node.js + TypeScript (Fastify). دلیل: تیم کوچک، یک زبان برای همه‌جا، کتابخانه‌های Meta آماده.
- **دیتابیس:** PostgreSQL، و pgvector برای جست‌وجوی کاتالوگ. دلیل: یک پایگاه برای همه‌چیز، نگهداری ساده‌تر.
- **صف:** Redis + BullMQ. Kafka/RabbitMQ در این مقیاس زیادی است.
- **پنل:** Next.js (RTL) + Tailwind، فونت وزیرمتن، موبایل‌محور چون صاحب‌فروشگاه بیشتر با گوشی کار می‌کند.
- **LLM:** لایه انتزاعی با دو مدل: ارزان و سریع برای بیشتر پیام‌ها، قوی‌تر برای موارد مبهم. مدل‌ها قابل تعویض باشند.
- **هاستینگ:** VPS خارج از ایران با Docker Compose؛ اول یک سرور، بعد جداسازی.

**جریان پیام:**
```
اینستاگرام (Meta) --وب‌هوک--> [API: تأیید امضا]
   -> ذخیره پیام خام + شناسه یکتا (ضد تکرار)
   -> [صف BullMQ]
   -> [Worker]
        1. بارگذاری مکالمه و اطلاعات فروشگاه
        2. جست‌وجوی محصول/قیمت (Postgres/pgvector)
        3. فراخوانی LLM با پرامپت فروشگاه
        4. بررسی خروجی: قیمت‌ها از دیتابیس باشد، نه ساخته‌ی مدل
        5. اطمینان پایین؟ -> «نیاز به انسان» + اعلان به صاحب فروشگاه
   -> [Meta Send API] -> پاسخ به مشتری
   -> لاگ + نمایش در پنل
```
وب‌هوک باید سریع ۲۰۰ بدهد و کار سنگین در صف انجام شود.

**نکات ایران:**
- اینستاگرام فیلتر است. خود محصول روی سرور خارجی اجرا می‌شود، اما پنل باید برای کاربر ایرانی بدون فیلترشکن باز شود (دامنه/CDN قابل دسترس یا بخشی از مدیریت از طریق بله/تلگرام). نیاز به آزمایش واقعی دارد.
- پرداخت به Meta و ارائه‌دهندگان LLM برای ایرانی‌ها دشوار است؛ احتمالاً حساب یا شرکت خارج از ایران لازم است. جنبه حقوقی باید با مشاور بررسی شود.
- هزینه LLM دلاری و درآمد ریالی است؛ نوسان ارز ریسک است. قیمت ریالی با حاشیه امن و سقف مصرف برای هر فروشگاه.
- فارسی محاوره («موجوده؟»، «چند میشه؟»)، فینگلیش و ارقام فارسی/انگلیسی: نرمال‌سازی متن (ی/ک، ارقام) و مجموعه تست واقعی لازم است.
- پرداخت اشتراک کاربران: درگاه ایرانی.

**مصالحه‌ها:**
- مدل خارجی (فارسی بهتر، شروع سریع) در برابر مدل باز میزبانی‌شده (کنترل هزینه، ولی GPU و کار بیشتر): شروع با API، سنجش بعدی.
- VPS در برابر Serverless (Cloudflare Workers): VPS برای شروع ساده‌تر است.
- ابزار بدون‌کد (n8n/Zapier) برای نمونه اولیه خوب است، برای مقیاس و کنترل خطا محدود.
- فقط API رسمی Meta؛ روش‌های غیررسمی خطر مسدود شدن حساب مشتری دارند.

**نامطمئن (به گفته نگار):** شرایط دقیق App Review، هزینه واقعی هر پیام با LLM (بدون اندازه‌گیری عدد نمی‌دهیم)، امکان اتصال حساب‌های فروشگاه‌های ایرانی به API رسمی، اثر قطعی/کندی اینترنت ایران بر پنل، و قانونی بودن ارائه سرویس و پرداخت در شرایط تحریم.

## طرح رضا (مهندس داده)

**جدول‌ها (PostgreSQL، ساده‌شده):**
```sql
shop(id PK, name, timezone, plan, created_at)
owner_user(id PK, shop_id FK, email, password_hash, role, created_at)

ig_connection(id PK, shop_id FK, ig_user_id UNIQUE, ig_username,
  access_token_enc,        -- رمزنگاری‌شده
  token_expires_at, scopes, status, connected_at)

customer(id PK, shop_id FK, ig_scoped_id, display_name,
  UNIQUE(shop_id, ig_scoped_id))

conversation(id PK, shop_id FK, customer_id FK,
  last_customer_msg_at,    -- برای پنجره ۲۴ ساعته
  status ENUM(bot, handoff, closed))

message(id PK, conversation_id FK, ig_message_id UNIQUE,  -- ضد تکرار
  direction ENUM(in,out), sender ENUM(customer,bot,human),
  text, media_json, sent_at, delivery_status)

product(id PK, shop_id FK, name, description, price_rial BIGINT,
  stock_qty INT, stock_updated_at, active)
kb_article(id PK, shop_id FK, title, body, embedding NULL, updated_at)

handoff(id PK, conversation_id FK, reason, status, assigned_to FK owner_user,
  created_at, resolved_at)
event_log(id PK, shop_id FK, conversation_id NULL, type, payload_json, created_at)
webhook_raw(id PK, received_at, signature_ok, body)  -- نگهداری کوتاه‌مدت برای دیباگ
```
نکته‌ها: قیمت به ریال و عدد صحیح؛ موجودی زمان آخرین به‌روزرسانی دارد و بات نباید موجودی کهنه را قطعی اعلام کند؛ همه کوئری‌ها `shop_id` دارند (مثلاً Row Level Security).

**اتصال به API اینستاگرام (طبق دانش رضا، نیازمند راستی‌آزمایی):**
1. فقط حساب Professional (Business/Creator).
2. OAuth: «Instagram Login» ساده‌تر از «Facebook Login» (نیازمند Page) است؛ باید بررسی شود کدام مناسب‌تر است.
3. توکن کوتاه‌مدت به بلندمدت (حدود ۶۰ روز) تبدیل و پیش از انقضا تمدید شود؛ زمان‌بند تمدید لازم است.
4. وب‌هوک: تأیید اولیه با `hub.verify_token` و `hub.challenge`؛ برای رویدادها، امضای `X-Hub-Signature-256` (HMAC-SHA256 روی بدنه خام، مقایسه زمان‌ثابت)؛ پاسخ سریع ۲۰۰ و پردازش در صف؛ حذف تکراری با `ig_message_id`.
5. ارسال با Send API؛ قبل از ارسال، `last_customer_msg_at` چک شود. پنجره معمولاً ۲۴ ساعت است (تگ Human Agent تا ۷ روز برای پاسخ انسانی)؛ پیام تبلیغاتی آغازگر مجاز نیست.
6. برای حساب مشتریان باید مجوزهایی مثل `instagram_business_manage_messages` را با App Review بگیریم؛ احتمالاً Business Verification و سیاست حریم خصوصی هم لازم است. زمان و سختی تأیید معلوم نیست.

**نامطمئن (به گفته رضا):** نام دقیق مجوزها، نسخه Graph API و آدرس‌ها؛ نرخ محدودیت دقیق (عددی نداریم و نباید قطعی نقل شود)؛ امکان ثبت‌نام توسعه‌دهنده، تأیید اپ و Business Verification با مدارک ایرانی.

**ریسک‌های داده و حریم خصوصی:**
- توکن‌ها دسترسی کامل به دایرکت می‌دهند: رمزنگاری با کلید جدا، دسترسی حداقلی، امکان ابطال.
- مکالمه‌ها ممکن است آدرس و تلفن داشته باشند: حداقل‌سازی، مدت نگهداری مشخص، ماسک کردن لاگ‌ها.
- ارسال به LLM خارجی: مشتری و فروشگاه باید مطلع باشند؛ محل سرورها اثر حقوقی دارد.
- Meta آدرس حذف داده و سیاست حریم خصوصی می‌خواهد؛ حذف مشتری و فروشگاه باید پیاده شود.

## ریسک‌های فنی
۱. **دسترسی به API و سیاست Meta (حیاتی‌ترین):** رد شدن App Review یا محدود/قطع شدن دسترسی کل محصول را متوقف می‌کند. تأیید برای ایرانی‌ها فرض نشود. تحریم و فیلتر بودن اینستاگرام ریسک را بیشتر می‌کند.
۲. **پاسخ نادرست AI:** قیمت یا موجودی غلط خطای تجاری است. راه‌حل: قیمت و موجودی فقط از دیتابیس، لاگ همه پاسخ‌ها، ارجاع به انسان در اطمینان کم یا شکایت.
۳. **سرویس‌های خارجی:** فیلتر، قطعی، تحریم LLM و پرداخت. راه‌حل: لایه انتزاع مدل، مدل پشتیبان، صف با تلاش مجدد.
۴. **انقضای توکن:** بدون پایش، پاسخ‌دهی بی‌صدا قطع می‌شود؛ هشدار به مالک لازم است.
۵. **پیام تکراری یا خارج از پنجره پاسخ:** با قید یکتایی، پردازش idempotent و بررسی پنجره قبل از ارسال.
۶. **زبان فارسی محاوره:** خطای مدل؛ با نرمال‌سازی و تست روی داده واقعی کم می‌شود، حذف نمی‌شود.
۷. **حریم خصوصی و حقوقی:** نگهداری داده مشتری، ارسال به مدل خارجی و ارائه سرویس در شرایط تحریم؛ نیاز به مشاور حقوقی.
۸. **هزینه LLM دلاری در برابر درآمد ریالی:** تا اندازه‌گیری روی پیام‌های واقعی، هزینه هر پیام را نمی‌دانیم.

## قدم بعدی
۱. راستی‌آزمایی رسمی Instagram Messaging API با مستندات Meta: نوع حساب، مجوزها، App Review، Business Verification، پنجره پاسخ، محدودیت نرخ؛ و بررسی اینکه برای شرکت و مشتریان ایرانی ممکن است یا نه. تا روشن نشود، سرمایه‌گذاری سنگین توصیه نمی‌شود.
۲. تست کیفیت فارسی ۲–۳ مدل زبانی روی نمونه ناشناس‌شده از دایرکت‌های واقعی، و اندازه‌گیری هزینه هر پیام.
۳. نمونه حداقلی با ۳ تا ۵ فروشگاه واقعی: وب‌هوک + صف + دیتابیس + پاسخ از کاتالوگ، تا نامعلوم‌ها با داده پاسخ بگیرند.
۴. تصمیم درباره محل میزبانی، پرداخت و بررسی الزامات حقوقی با مشاور.
